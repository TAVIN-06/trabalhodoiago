Página 1 – A diferença entre Git e GitHub

Git é um sistema de controle de versão distribuído (DVCS) criado para ajudar os desenvolvedores a rastrear e gerenciar as alterações em seus códigos.

Quer você esteja corrigindo um bug, adicionando um novo recurso ou experimentando uma ideia arriscada, o Git facilita o salvamento de diferentes versões do seu projeto, para que você possa sempre voltar atrás se algo quebrar.

Página 2 – Git vs GitHub (Continuação)

O papel do GitHub na colaboração

Se o Git é o mecanismo de controle de versão, o GitHub é a garagem onde as equipes se reúnem para construir juntas. Ele se baseia nos recursos locais do Git, oferecendo uma plataforma baseada em nuvem para hospedar repositórios Git - transformando esforços individuais em progresso coletivo.

Ao armazenar seu código em um local centralizado, o GitHub permite que sua equipe acesse, revise e contribua com o mesmo projeto, independentemente de onde estejam. Ele adiciona uma camada rica de ferramentas de colaboração que ajudam na comunicação e na coordenação.

Resumo da integração

Git é a ferramenta subjacente que gerencia as versões de código localmente, enquanto o GitHub dá um passo adiante, oferecendo uma plataforma colaborativa para hospedar esses repositórios on-line. O Git lida com o rastreamento e o armazenamento de alterações, e o GitHub fornece a camada extra de colaboração, gerenciamento de projetos e recursos de comunidade. Essa integração ajuda as equipes a trabalhar com mais eficiência e a manter um histórico coerente do projeto.

Página 4 – O que é um Repositório e Repositório Local

O que é um repositório

Um repositório (ou repo) é um lugar central onde todos os arquivos, códigos, documentos e recursos de um projeto ficam guardados. É tipo um centro que mantém tudo organizado e acessível para sua equipe.

O repositório local

O repositório local é o repositório que criamos em nosso computador, nele adicionamos os nossos arquivos e vamos registrando as mudanças com os commits. Esse repositório é chamado de local, porque ele existe apenas em nosso computador e não está conectado na internet.

Página 5 – Repositório Remoto

Um repositório remoto é um repositório Git armazenado em outro lugar, geralmente em um serviço como o GitHub.

Ele continua sendo um repositório Git, mas fica disponível pela rede, e não só na sua própria máquina.

Página 7 – O que é um Commit

Um commit adiciona as alterações mais recentes do código-fonte para o repositório, tornando essas alterações parte da revisão principal do repositório.

É importante ressaltar que os commits nos sistemas de controle de versão são mantidos no repositório indefinidamente.

Página 8 – O Histórico de Commits como Diário de Bordo

Porque o commit é como um diário de bordo?

Um commit no GitHub pode ser comparado a uma espécie de diário de bordo de um projeto. Cada vez que fazemos uma alteração importante no código, podemos criar um commit para registrar o que foi feito.

Dessa forma, o histórico do projeto mostra como ele foi evoluindo ao longo do tempo.

Página 9 – Exemplo Concreto de Problema que o Git Resolve

Um exemplo concreto de problema que o Git resolve é quando duas pessoas estão trabalhando no mesmo projeto e acabam modificando o mesmo arquivo.

Sem o Git, seria necessário ficar enviando arquivos atualizados uns para os outros, o que poderia causar confusão e até fazer alguém perder alterações.

Com o Git, cada pessoa pode registrar suas alterações em commits e, depois, juntar as diferentes modificações. Além disso, se o código que funcionava ontem parar de funcionar hoje, é possível consultar o histórico de commits para descobrir o que foi alterado e voltar para uma versão anterior que estava funcionando.

Página 10 – O arquivo .gitignore

O que é o gitignore:

O arquivo .gitignore é um arquivo de texto que diz ao Git quais arquivos ou pastas ele deve ignorar em um projeto. Para criar um arquivo .gitignore local, crie um arquivo de texto e dê a ele o nome de .gitignore (lembre-se de incluir o . no começo). Em seguida, edite esse arquivo conforme necessário. Cada nova linha deve listar um arquivo ou pasta adicional que você quer que o Git ignore.

Por que colocar a senha nele?

Senhas, chaves de acesso e arquivos de configuração locais nunca devem entrar no repositório por três motivos principais: segurança, flexibilidade e integridade do ambiente.

Página 11 – Comandos Básicos: git init e git clone

Início dos comandos básicos do Git:

a) git init

O que faz: Cria um novo repositório Git vazio na pasta atual.

Quando se usa: Ao iniciar um novo projeto do zero na sua máquina.

Exemplo: git init

b) git clone

O que faz: Baixa uma cópia completa de um repositório remoto existente para o computador.

Quando se usa: Para clonar um projeto da nuvem (como do GitHub) e começar a trabalhar nele.

Exemplo: git clone https://github.com/usuario/projeto.git

Página 12 – Comandos Básicos: git status, git add e git commit

a) git status

O que faz: Exibe o estado atual dos arquivos na working tree (quais foram modificados, quais estão prontos para commit e quais não são rastreados).

Quando se usa: Sempre que quiser verificar quais alterações foram feitas antes de salvá-las.

Exemplo: git status

b) git add

O que faz: Adiciona as alterações dos arquivos para a área de preparação (staging area).

Quando se usa: Para selecionar quais arquivos modificados farão parte do próximo commit.

Exemplo: git add .

c) git commit -m

O que faz: Salva permanentemente os arquivos preparados no histórico do repositório junto com uma mensagem descritiva.

Quando se usa: Para registrar um marco ou alteração concluída no código.

Exemplo: git commit -m "feat: cria a tela de login"

Página 13 – Comandos Básicos: git push e git pull

a) git push

O que faz: Envia os commits locais realizados na sua máquina para o repositório remoto na nuvem.

Quando se usa: Para compartilhar suas alterações atualizadas com a equipe no GitHub.

Exemplo: git push origin main

b) git pull

O que faz: Baixa e integra automaticamente as alterações mais recentes do repositório remoto para o seu repositório local.

Quando se usa: Para atualizar o seu computador com o trabalho que outros colegas enviaram para a nuvem.

Exemplo: git pull origin main

Diferença: O push envia o seu código para fora (da sua máquina para a nuvem), enquanto o pull traz o código de fora para dentro (da nuvem para a sua máquina).

Página 14 – Comandos Básicos: git log e git diff

a) git log

O que faz: Lista todo o histórico de commits do projeto em ordem cronológica reversa.

Quando se usa: Para ver quem fez o quê, quando e quais foram as mensagens de commit anteriores (use git log --oneline para ver de forma resumida).

Exemplo: git log --oneline

b) git diff

O que faz: Mostra as diferenças exatas (linhas adicionadas e removidas) nos arquivos modificados que ainda não foram adicionados ao staging.

Quando se usa: Para revisar detalhadamente o que mudou no código antes de rodar o comando git add.

Exemplo: git diff

Página 15 – Comandos Básicos: git restore

a) git restore

O que faz: Descarta as alterações locais feitas em um arquivo, retornando-o para o último estado salvo no repositório.

Quando se usa: Quando você fez testes que deram errado e quer desfazer as mudanças em um arquivo específico.

Exemplo: git restore index.html

Por que material antigo ensina git checkout -- arquivo? Antigamente o comando checkout acumulava muitas funções (trocar de branch e restaurar arquivos), o que gerava confusão nos iniciantes. O Git moderno introduziu o git restore para separar e simplificar essa tarefa de descarte.

Página 16 – Comandos Básicos: branch, switch e merge

a) git branch

O que faz: Cria, lista ou deleta ramificações (branches) no repositório.

Quando se usa: Para ver quais branches existem ou criar uma nova ramificação isolada.

Exemplo: git branch nova-feature

b) git switch

O que faz: Alterna o contexto de trabalho para uma branch específica (antigamente feito com checkout).

Quando se usa: Quando você quer mudar de branch para trabalhar em outra parte do projeto.

Exemplo: git switch main

c) git merge

O que faz: Junta o histórico e as alterações de uma branch secundária na branch em que você está atualmente.

Quando se usa: Para unificar o recurso pronto de uma branch com o código principal (main).

Exemplo: git merge feature/login

Página 17 – Tópico 3: Branches e Forks

Explicação dos três mecanismos que permitem várias pessoas mexerem no mesmo código sem se atropelar:

a) O que é um Branch?

  • É uma linha de desenvolvimento separada em um projeto.
  • Funciona como uma cópia segura do estado atual do código.
  • Permite testar ideias ou criar recursos sem risco de quebrar o sistema.

I. O que acontece com o “main” enquanto se trabalha em outra branch? Permanece intacto, estável e funcionando isoladamente.

II. O que é um Merge? Processo de juntar o trabalho de duas ramificações diferentes aplicando no main.

b) O que é um Fork?

É uma duplicata exata do projeto original, mas sob o seu total controle e propriedade, funcionando de forma independente.

Página 18 – Tópico 3: Pull Request e Caminho de Contribuição

c) O que é um “Pull Request”?

Uma solicitação formal para incluir as alterações de código que você fez em uma branch ou fork dentro do repositório principal do projeto.

  • Code Review: Evita bugs em produção, mantém o padrão do projeto e compartilha informações com a equipe.
  • Quem aprova: Engenheiros mais experientes, donos do repositório Open Source ou você mesmo em projetos solo.

d) Caminho completo de uma contribuição (passos):

  1. Faça o Fork do repositório original.
  2. Clone o seu Fork para o computador.
  3. Altere o código e faça commits (git add e git commit).
  4. Abra o Pull Request para o projeto original.

Página 19 – Tópico 4: Introdução ao Git Flow

Git Flow não é um comando nem um programa: é um combinado de equipe sobre como usar as branches.

a) Para que serve o Git Flow?

Serve para padronizar e dar previsibilidade ao ciclo de vida do software. Resolve problemas recorrentes como código de produção quebrando constantemente, histórico de commits bagunçado, e desenvolvedores apagando o trabalho uns dos outros.

Página 20 – As Branches do Git Flow

b) Papel de cada branch:

  • I. “Main”: Branch de produção. Guarda o histórico oficial e reflete o código que está rodando com o cliente final; deve estar estável.
  • II. “Develop”: Branch de integração. Linha de montagem onde o trabalho novo da equipe se junta para a próxima entrega.
  • III. “Feature/”: Usada para desenvolver novas funcionalidades; nasce da develop e volta para ela via Pull Request.
  • IV. “Release/”: Fase de preparação, testes finais e correção de pequenos bugs para lançamento de nova versão.
  • V. “Hotfix/”: Linha de emergência médica para corrigir bugs críticos encontrados na main imediatamente.

Página 21 – Nomenclatura e Padronização de Branches

c) Nomenclatura de branch:

Por que feature/login-com-google é melhor que minha-branch-2?

  • Informa o contexto e o escopo imediatamente: O prefixo feature/ indica nova funcionalidade e o complemento explica o que está sendo construído.
  • Remove a dependência pessoal: Evita nomes genéricos como "minha", permitindo que qualquer pessoa saiba o propósito da branch caso o desenvolvedor saia da equipe.

Página 22 – Quem Usa o Git Flow

d) Empresas e projetos reais que adotam Git Flow:

Muitas corporações de setores tradicionais, serviços financeiros e consultorias de TI adotam o Gitflow para manter controle rigoroso de versões, isolamento de produtos e regulação financeira.
